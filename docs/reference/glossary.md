# Glossary reference

The words these pages, the code and the UI use, with the exact meaning each has in MRR AI. Where a
word means something different in the code than in everyday speech, the code meaning is given.

Source of truth: the code named in each entry.

## The record and its parts

| term | meaning |
| --- | --- |
| **Record** | One uploaded medical-record PDF. The UI says "record"; the code and database say **document** (`documents` table, `Document` model). The two words mean the same thing. |
| **Aggregate record** | Several already-split PDFs uploaded together and merged into one record (`POST /api/documents/aggregate`, the "split upload" in the UI). Each source file becomes one row, categorized by a `classify` job instead of being segmented. |
| **Sub-document** | One report, note, study or letter inside a record, as a page range. The unit that is categorized, checked for duplicates and summarized. |
| **Row** | A sub-document as stored: `review_rows` (the reviewer's working set) or `segment_rows` (the machine's original output). Carries start and end page, category, title, date, author, `include`, `flag` and `method`. |
| **Include** | Whether a row goes into duplicate checking, summarizing and export. Chosen by the reviewer. A new row starts with its category's summarize default (`catalog.summarize_default_for`); General (100) is the category seeded off. |
| **Flag** | `x` on a row the pipeline was not confident about and wants a human to look at; `-` otherwise. Set by `segment_engine` when categorization needed review or timed out, and by the verify pass. |
| **Method** | Which path of the categorization cascade decided the row's category: `rules`, `llm+embedding` (both agreed), `llm-only`, `embedding-only`, `llm-disagree`, `no-signal`, `empty`, or `timeout`. See [Categorization](../explanation/categorization.md). |
| **Header** | The report header fields on a record: patient name and date of birth, law firm, attorney, doctor, letter type and date, pages received. Filled by the reviewer or by **Auto-fill** from the first pages. |
| **Page text** | The text of one page, extracted once (from the PDF's text layer or by OCR) and stored in `page_texts` so no page is OCR'd twice. See [OCR and page text](../explanation/ocr-and-page-text.md). |

## Pipeline

| term | meaning |
| --- | --- |
| **Identification** | The UI word for the segment job: finding the sub-documents and categorizing them. |
| **Segmentation** | Finding where each sub-document starts and ends. |
| **Window** | A slice of consecutive pages sent to the model in one segmentation call. Neighbouring windows overlap. |
| **Seam** | The pages where two windows overlap. Each seam page is decided by the window that also saw the page before it. |
| **Category** | The document type of a sub-document, an id such as `1` or `13`, with `100` meaning General (the fallback). |
| **Catalog** | The set of categories and their summary prompts. Stored in the `categories` and `prompts` tables and editable by an admin; the code constants in `taxonomy.py` and `prompts.py` are used only while the `categories` table is empty. |
| **Catalog revision** | A counter in `catalog_meta` bumped by every admin edit, so running workers reload the catalog and each job records which catalog it used. |
| **Cascade** | The categorization order: title rules first, then an embedding model and a constrained LLM call that must agree. |
| **Verify pass** | In segmentation: a yes/no model check of suspect boundaries that can only **suggest** merges to the reviewer. Not the same as the audit. |
| **Injury date (DOI)** | The date of injury, read once per row at the end of segmentation and prefixed to summaries. |
| **Duplicate check (dedup)** | The reviewer-started job that groups included rows that look like copies of each other and asks a model to confirm. |
| **Duplicate group** | Rows the duplicate check believes are copies of one another. The reviewer keeps one, dismisses the group, or removes a member. |
| **Summary** | The generated text for one included sub-document, stored in `summaries`. |
| **Audit** | The model call that checks a drafted summary against its source and may return a corrected version, subject to guards. Recorded as `verified` on the summary. |
| **Notice** | A code-written line added to a summary, for example that some pages were unreadable. Never generated by the model. |
| **Deposition** | A transcript of sworn testimony (category 9). Summarized in groups of ten transcript pages, citing transcript page numbers. |
| **Bundle** | A category-filtered deliverable: the matching sub-documents as one PDF with a cover page, or as a summarized report. |
| **Linked PDF** | The review letter with the source record appended and each entry linked to its pages. |

## Jobs and workers

| term | meaning |
| --- | --- |
| **Job** | One run of one pipeline stage for one record: a `jobs` row plus an RQ job with the same id. |
| **Job kind** | `segment`, `classify`, `dedup` or `summarize`. |
| **Job state** | Where the job is: active (`queued`, `running`, `paused`) or finished (`done`, `needs_attention`, `error`, `interrupted`, `cancelled`). Only one active job per record. Full list: [Job and document states](job-and-document-states.md). |
| **Stage (progress)** | The step a running job reports, such as `segmenting`, `categorizing` or `injury-dates`, shown in the progress bar. |
| **Stage (model)** | A kind of model call with its own backend, model and thinking setting, such as segment, classify or summarize. See [Model calls by stage](model-calls-by-stage.md). Not the same as a progress stage. |
| **Document status** | Where the record stands: `uploaded`, `segmenting`, `reviewing`, `summarizing`, `done`, `needs_attention`, `interrupted` or `error`. A failed job moves a record only out of the stage that job put it in. |
| **needs_attention** | A run that finished but could not do some sub-documents; it names them. |
| **Paused** | A summarize run waiting to resume by itself after the model provider pushed back. |
| **Stop / Force stop** | Stop asks the running job to end at its next checkpoint; Force stop kills the worker's job process and finalizes the job from outside. |
| **Lane** | A per-user queue, such as `segment:2`, so one user's backlog cannot hold up another's. Workers serve lanes round-robin. |
| **Orphan recovery** | The check at API startup that finds jobs whose worker died and finalizes them. |

## Models and configuration

| term | meaning |
| --- | --- |
| **Backend (model)** | Which provider serves a model call: `gemini` (Vertex AI or the Gemini Developer API), `openai`, or `vllm` (a self-hosted OpenAI-compatible server). |
| **Provider seam** | The single interface every model call goes through, which picks the backend, model and thinking setting for each stage. See [Model providers](../explanation/model-providers.md). |
| **Pacer** | The shared, Redis-backed rate limiter that spaces model calls across all workers and slows down when the provider returns 429. |
| **Provenance** | What each job and summary records about how it was made: the build (`build_sha`), prompt fingerprint, catalog revision, backend and model names. `NULL` means "not recorded", never a default. |
| **Passthrough** | Naming a setting in `docker-compose.yml` so a value in `.env` reaches a container. A setting not named there never arrives. See [Configuration model](../explanation/configuration-model.md). |

## People and roles

| term | meaning |
| --- | --- |
| **Reviewer** | A signed-in user who uploads and reviews records. Sees only their own records. |
| **Admin** | A user with the admin flag (`is_admin`, exposed as `is_superuser`). Can edit the catalog and reprocess records. Granted only with the CLI. See [Manage users and admins](../how-to/manage-users-and-admins.md). |
| **Operator** | Whoever runs the server: deploys, backs up, reads logs. Not a role in the app. |
